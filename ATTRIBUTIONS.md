## File Format Compatibility

The project reads or writes public and ecosystem file formats for interoperability:

- Aseprite-compatible JSON export structures for sprite tags and slices. The emitted `editor_metadata.json` schema is original project code for interoperability and does not bundle third-party editor code or assets.
- Godot-compatible NPC metadata and sprite assets.
- RPG Maker compatible character sheet outputs.
- OCAD-style one-image all-actions sprite sheet outputs.
- LDtk-compatible project JSON exports for scene tile maps and entity definitions. The writer is original project code for interoperability and does not bundle LDtk editor code, plugins, or assets.
- Tiled-compatible JSON and TSX exports. The writers are original project code
  for interoperability and do not bundle Tiled editor code or assets.
- Standard JSON atlas and metadata files used by browser preview flows.

Where a format is learned from public documentation or observable files, the implementation should remain independently written in this repository.

## Algorithms

- The deterministic 2.5D rule-map path uses an original repository
  implementation of AC-3 constraint propagation plus backtracking. It uses the
  public algorithmic idea and does not copy a third-party implementation.

## Inspiration And Research

The project is informed by common workflows in pixel-art and game-asset tools, including browser sprite utilities, sprite sheet exporters, animation tag schemas, and game engine import pipelines.

Competitor or ecosystem product names may appear in research notes only to describe compatibility targets or prior art. They must not be used as this project's brand, package name, generated metadata identifier, or replacement claim.

The v0.5 Editor Workspace direction also uses clean-room behavior research from
public 2D editor workflows supplied by the project owner. No source code,
assets, templates, private APIs, runtime implementation, or product branding
from those tools is copied or bundled.

Pixel grid refinement behavior is informed by public discussions and product
descriptions of pixel-grid detection, pixel-perfect cleanup, and shared palette
locking workflows, including perfectPixel, proper-pixel-art, and
perfectpixel-studio references named in the project protocol. The implementation
in `src/character-pack/pixelGridRefinement.js` is original repository code: no
external source code, assets, templates, private APIs, or bundled binaries are
copied.

The optional Pixel Grid v2 palette-matching path uses an original implementation
of the public OKLab color-space equations described by Björn Ottosson at
`https://bottosson.github.io/posts/oklab/`. Only deterministic color-distance
math is used; no external source code, dependency, asset, or model is copied or
bundled.
