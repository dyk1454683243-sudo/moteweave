## 1. 目标、现状与边界

解决持续编辑使 `project.json` 内完整修订索引和操作回执不断增长、最终碰到 2 MiB 后无法保存的问题。采用“小的当前状态 + 磁盘上的完整历史”，不是提高原上限或截断历史。

- 不删除任何已提交历史、回执、manifest、像素块；不合并用户操作，不减少撤销记录。
- 每次有效松手仍自动保存一次；零位移、取消、重试、Undo/Redo 沿用原语义。重试同一次提交不增加新历史。
- 不改变文字越界裁剪、选区、绘制、导出、accepted 权限或原始资产不可变规则；不新增历史面板、定时保存、后台压缩或自动清理。
- 不动去背、生成产物、真实项目和无关 dirty。方案确认后仅在隔离测试数据验证迁移；不 stage/commit/push，确认方案不等于授权推送。
- “完整历史”指现在实际保存的全部文档修订和操作回执，不虚构过去未记录的项目快照，也不承诺新增跨刷新无限 Undo 界面。

证据：实际 256×256、4 帧 3 层项目在 100 次业务写入后索引为 63,337 B；按当前格式推算约累计 3,699 次此类写入达到上限。这是序列化推算，不是数千次实跑，也不是用户实际绘画速度。每次约 562–566 B 的增长来自持久索引，不应靠删记录消除。

已有证据位于 `/private/tmp/gametool-text-save-stability-xL8iHG/index-capacity-estimate.json` 和同目录 `index-boundary-report.json`、`index-boundary-api-report.json`。旧“索引受控”结论只证明越限安全拒绝，并未解决长时间可编辑容量。

## 2. 推荐的数据结构

提出显式项目存储版本 `editor_project_v2`；`sprite_document_v1` manifest、像素块、文档修订号及内容哈希语义不变。正式协议在用户确认后补齐，不能悄悄改变 v1 格式。

| 部分 | 保存内容 | 读取方式 |
| --- | --- | --- |
| `project.json` 当前根 | 项目当前字段、画布、各文档 working/accepted 指针及对应 manifest 哈希、两个历史索引根哈希、存储版本 | 打开项目及每次确认保存只读这一小份；保留 2 MiB 防护 |
| 修订索引页 | 键为文档 ID + 修订号；值保留 manifest 哈希、父修订、时间等原记录 | 按指定修订查找；分页遍历仅供内部核验 |
| 操作回执索引页及回执记录 | operation ID → 不可变回执记录哈希；记录保留原 payload 哈希和完整原回执，包括非像素操作的附加恢复字段 | 按 operation ID 查找，不淘汰旧回执 |
| 原 manifest / blocks | 所有已提交版本的完整内容 | 继续使用原路径与校验，不复制整份像素历史 |

两个索引使用**专用、有界页、写时复制的平衡查找树**：页按内容哈希寻址，旧页不覆盖；一次新增只写受影响的叶、祖先和分裂页。根只存两个哈希，不能保存所有页的列表；也不能退化成每次遍历整条历史日志。不是新建通用数据库框架，不引入数据库依赖。

拟定页上限 16 KiB；完整回执放在单独不可变记录中，树内只放引用，避免带恢复快照的合法旧回执放不进页。单回执记录保留旧整个项目 2 MiB 所能容纳的字节范围，不截字段；迁移测试须覆盖所有现有回执类型。后端索引页/回执记录缓存按字节合计限额 8 MiB，淘汰缓存不删磁盘记录；前端不长期持有完整历史索引。页格式、最大树深、键排序、哈希校验和异常路径在实现协议中固定，并以分裂/深度边界测试验证。

所有已提交记录必须仍从**当前已提交根**可达；索引重排或分裂不能使旧记录丢失。未发布准备页不能因文件存在、序号较小或后来有新保存就成为已提交记录。当前/accepted 指针与索引必须一致。数字修订仍限制为安全整数，磁盘不足等原安全边界保留；不是无限存储承诺。

这是必要的复杂度：只把历史移到另一个大 JSON，仍会整包加载；把所有分片名放进根，根仍会撞上限；单链日志会使冷启动的旧回执查询随历史长度线性变慢。采用索引页后需实测写放大，不能只报告根文件缩小。

## 3. 旧项目兼容与升级

| 输入/客户端 | 推荐处理 |
| --- | --- |
| v0 项目及旧入口 | 保留原行为；原 v0→独立 v1 副本流程及来源不变，不原地改 v0 |
| 已有 v1，仅打开、列项目、导出或读历史 | 新版原样读取，不写文件、不顺手迁移 |
| v1 重放已经成功的 operation ID | 先按原回执返回；同 ID 不同 payload 仍冲突；不因重放触发升级 |
| v1 首次新的有效变更 | 在原项目互斥锁内，迁移 + 本次编辑合成一次发布；项目和文档只按该编辑正常增修订 |
| v2 项目 | 新版直接按小根 + 按需索引读写；新建像素项目采用 v2 |
| 旧客户端/旧写入路径面对 v2 | 明确拒绝不兼容写入，不能降级、伪装成 v1 或覆盖新格式 |

首次升级先校验 v1，保留一份**原始 v1 `project.json` 字节备份**及其哈希（最多原有 2 MiB），不复制仓库、依赖、manifest 或像素目录。逐条保留所有旧索引/回执、文档 ID、修订/父链、时间、working/accepted、来源关系；对引用完整性流式核验，遇到损坏不跳过、不发布。

备份和迁移准备可按源哈希复用，未成功的重试不得每次复制一套备份。只读目录、空间不足、旧数据损坏、版本不支持时，在换头前拒绝并保留旧项目；旧 v1 已到 2 MiB 仍须能由新版首次有效写入升级，不能先调用旧追加序列化再迁移。

升级不是独立用户动作，不额外创建业务修订/撤销/回执，也不改变本次请求的 ID 或 payload 哈希。首次写入的旧预期修订仍有效；锁内重新核验版本和预期修订，两个客户端不能各自覆盖对方的迁移。

**兼容边界：**升级后不能承诺旧软件还能写。新版后端需对旧 POST overwrite、PUT、autosave、import、delete/unlink、旧 export-pack 和底层 store 执行 fail-closed：旧写者只允许实际磁盘版本 v0，而非仅排除 v1；伪造请求 version 不能绕过锁内版本判断。旧后端离线直接操作文件不受新版进程控制，必须验证已发布旧版本会安全拒绝 v2；若存在破坏路径，先报告并补兼容保护，不能宣称向后写兼容。运行旧后端和新后端同时修改同一目录不在支持范围。

备份只恢复升级前的旧状态，不是升级后新编辑的完整回退。换头成功后不自动降级或用备份覆盖新历史；软件回退只能用能读 v2 的修复版本，数据降级/恢复另行授权。

## 4. 原子保存与崩溃恢复

复用项目锁、安全路径/文件身份校验、原 expected revision 和操作权限。一次写入按以下顺序完成：

1. 在锁内读取一个已提交根，先查完整回执，再校验请求与预期修订；读历史时绑定该根，不能拼接不同时刻的状态。
2. 准备新增像素块、manifest、索引叶及祖先页；校验哈希、记录引用和边界。首次迁移同时准备旧记录、备份和本次新增记录。
3. 新文件及所需目录完成落盘后，生成下一份小根；它同时引用新当前状态、修订索引和操作回执索引。禁止先发布 working 指针再补回执。
4. 在同一文件系统安全临时路径写根、fsync，然后原子替换 `project.json`，同步父目录。**这个根是唯一提交点**；不存在需要两个可变文件同时成功的提交。
5. 确认持久化后才回复成功；保存过程中的 UI 预览/右栏保持已有规则，不因切换存储重新整包加载。

| 中断点 | 允许结果与恢复 |
| --- | --- |
| 写页/manifest/备份失败，或换头之前退出 | 旧根仍有效；准备文件不成为历史，不删除旧数据；同 ID 重试安全复用/核验准备文件 |
| 原子换头时进程退出 | 重启只能读取完整旧根或完整新根；两者均有完整依赖，不能出现半新状态 |
| 根可能已换，但目录同步/响应失败 | 报未知结果，不假报未保存、不自动回滚；重启读取已提交根，用原 ID 判断是否已提交 |
| 已落盘但 ACK 丢失 | 原 ID + 原 payload 返回旧回执，不再写一份；同 ID 不同 payload 仍冲突 |
| 页缺失/哈希错误/非法路径 | fail-closed，报告存储错误；不扫描目录“猜”出历史、不静默回退到较旧内容 |

恢复依据提交根可达性，而不是最后一个文件名、时间戳或计数水位。仍保留已有 revision slot 避让与相同内容重用规则；不覆盖未决文件。失败准备文件记录大小，暂不自动清理；验收必须证明同一失败请求重复重试不会无界新增文件。

崩溃测试证明的是进程终止及注入的落盘失败；不能冒充真实断电测试或保证不遵守 fsync 的文件系统。支持范围与现有本地受管文件系统一致，不在本轮新增网络盘协议。

## 5. API、读取与产品接入范围

- 原保存端点、触发时机、权限、operation ID、expected revision、冲突及 unknown 恢复语义不变。所有现有专用项目变更通过同一 v1/v2 存储适配层，不能只修画笔而让文字、restore、布局、派生副本或接受操作另走旧路径。
- 新版专用变更请求增加 `X-Editor-Storage-Version: 2` 能力声明（不是权限），v1 首次新写和 v2 新写都要求它；缺失/未知值不进行迁移或写入，明确要求更新客户端。不将该传输头加入原业务 payload 哈希，旧 operation ID 的完整回执仍可由新版客户端重放。仅检查磁盘版本不足以防止仍开着旧缓存页面的客户端误写；Origin 和原 grant 校验不放宽，v0 旧入口不要求此头。
- v1 读取响应保留旧形状；v2 的 `project` 明确标记新版本，返回当前状态、working/accepted 对应记录及根引用，**不返回完整 `revisions` / `operation_receipts` map**。保存响应仍返回该次完整 receipt。客户端显式适配两个版本，不把字段缺失当空历史。
- 现有按指定 revision 读取 manifest、restore 和操作重放接口，经页索引查证已提交记录后继续工作；不新增全量历史下载端点或历史 UI。内部遍历有页/输出预算。
- 项目列表只读小根，原单索引 2 MiB、累计读取和响应预算不提高；不能为列项目或确认保存重建完整 v1 对象。缓存键必须包含项目身份与根哈希，切项目/重开后的迟到结果不得覆盖新上下文。
- 现有 typed 错误保留；v2 页/深度/根预算触顶为 `resource_limit`，旧写者为 `unsupported_project_writer`，损坏/落盘失败为受控存储错误，版本不支持明确拒绝。正式协议列出实际 HTTP 映射，不能用普通异常误报成功或吞掉错误。
- 界面布局与文案本轮不拟改变；实施前仍执行 design-to-implementation-contract。若数据绑定改变，按原规则同步 Current 对应说明/metadata 与矩阵，不改 Historical，不借机重做视觉。

## 6. 验收方案与通过标准

以下是**获批门槛**；本次实际结果和剩余项见 §8，不能把门槛本身当作通过证据。使用隔离的必要源码候选和小型合成输入，不迁移用户真实项目；原数据、历史证据、无关 dirty 原样保留。

| 验收组 | 必须证明 |
| --- | --- |
| 旧项目与迁移 | 空/普通/接近旧 2 MiB 上限、多文档、accepted、各种回执（含大于 16 KiB 和接近旧有效上限的合法回执）、脱离画布仍需保留的文档、旧 operation 重放；只读不改字节；首次保存只增正常一次修订；全部旧记录数/内容哈希逐项相同且可达；v0 不变；旧写者拒绝 |
| 原子性与恢复 | 在上述每个提交边界注入失败/终止，冷启动后只见完整旧/新状态；目录同步失败、磁盘写失败不使用真实填满磁盘方式；同 ID 重试、不同 payload 冲突、并发旧修订、首次迁移竞争均安全 |
| 索引正确性 | 叶/根分裂、跨页、键边界、旧回执查找、历史修订与 accepted 读取、缺页/坏哈希/非法路径、未发布孤儿页不被采信；最老/中段/最新历史均可 restore，且 restore 新增记录不删旧版本 |
| 长编辑容量 | 同一个最小真实 store 夹具连续累积至少 5,000 次有效保存（不是只拼 JSON，不重置项目凑次数），跨越本次约 3,699 次旧瓶颈；包括 draw/restore 类提交，另用真实页面覆盖文字移动；重启后继续保存并读取早期记录 |
| 内存与读写成本 | 同样当前画布/帧/层内容，在短/长历史下分别冷打开、保存、查旧回执；当前根和响应不线性携带历史，后端页缓存不超过 8 MiB；记录实际读写页数/字节、磁盘增量和耗时。若每写重写全历史、打开全历史或内存随全部索引持续增长，不能通过 |
| 产品回归 | 页面松手单写、零位移/取消不写、连续文字拖动不闪回、Undo/Redo、unknown 恢复、跨项目隔离、刷新/重启、PNG/图集完整 RGBA 和 JSON 语义；只比较匹配状态，不把历史被删或少保存当性能提升 |

5,000 次是本轮容量验证的最低证据，不是新产品保存次数上限，也不称作 5,000 次真人绘画。完整历史继续占用磁盘；报告需分开“用户历史字节”和“索引写时复制/失败准备的额外字节”，记录逻辑字节与实际磁盘占用。长检查前根据确定的页格式/树深估算新增页数与总量；旧 COW 页、回执记录、备份和失败准备也全部计入预算。若写放大使预算无法完成，先诊断页布局，不通过提高旧根上限、删历史或自动清理凑通过。

性能在相同机器/画布/操作下记录早段与后段保存延迟及独立纯持笔帧间隔；不把自动化鼠标往返时间当帧率。若出现可复现的随历史长度显著恶化，收口前解释并修复；本计划不虚报优化百分比或全浏览器绝对无泄漏。产品持有对象、浏览器/诊断开销分开记账。

资源与生命周期：

- 唯一 Codex runner 串行；其他代理仅只读审查，不启动测试、构建、浏览器或服务。
