# Frame Repair Live Quality Gate v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a provider-budgeted, eight-case live quality gate around the shipped single-frame repair flow, with an isolated benchmark project, blind human review, immutable evidence, and an honest three-state final result.

**Architecture:** A provider-free Setup operation copies six explicitly selected user-owned Character Packs and creates two deterministic repository controls in one new isolated Editor project. A pure canonical planner fixes all eight cases and one provider preset before any call. A quality-gate coordinator seals append-only evidence and derives progress, while every actual repair still travels through the existing per-case Frame Repair Plan, Generate, Recover, and specialized Accept authorities. The existing Workbench Canvas is reused inside a focused review layout; the browser never constructs trusted hashes, writes project JSON, or batches provider calls.

**Tech Stack:** Node.js ES modules, `node:test`, Sharp already present in the repository, existing Editor project store and Frame Repair service/coordinator, DOM and Canvas 2D, plain CSS, localStorage for non-authoritative recovery handles, and the checked-in process-tree resource supervisor.

### Recorded implementation binding for exact operation accounting

The canonical server plan assigns each case a deterministic `operation_id` after computing its `case_hash`:

```js
const operationId = `frqgop_${sha256(`${sessionId}\0${caseId}\0${caseHash}`).slice(0, 48)}`
```

This is an identity reservation inside the immutable plan, not an operation record and not a provider call. A pending case still has no ledger entry and contributes zero calls. When the user explicitly clicks the existing Generate action, the locked Frame Repair controller supplies this exact id to the existing lifecycle/live endpoint. Session loading can then query at most eight exact ids from the existing operation ledger, including an unknown/interrupted attempt that has no review or outcome file. It never enumerates operations, fabricates a job, or retries a call. Ordinary Frame Repair continues to generate its own random operation id.

### Safe derived states

The quality-gate view-model session states are exactly `planned`, `ready`, `running`, `paused`, `reviewing`, and `finalized`. Server evidence plus the existing in-browser Frame Repair lifecycle projects each case to exactly one of `pending`, `plan_ready`, `awaiting_confirmation`, `processing`, `outcome_unknown`, `provider_blocked`, `candidate_ready`, `quality_blocked`, `awaiting_review`, `awaiting_decision`, `accepted`, or `rejected`. The server never trusts a client-supplied state. These are quality-gate projections only; do not add them to the global Job status enum.
